The Terminal-First Workflow: Why Your Next Dev Setup Belongs in the Shell

August 20, 2026  |  Opened Terminal

Every developer has experienced the slow drift. You start the morning in your editor, open a browser tab for documentation, another for Slack, another for Jira, another for your CI dashboard, and before you know it, your screen is a mosaic of browser tabs and you have not written a single line of code. The context switching alone is exhausting before the first compile.

There is a better way. It is not new. It is not a SaaS product. It does not require a subscription. The terminal has been sitting right there the entire time, waiting for you to use it properly. This article is about building a terminal-first workflow that keeps you in the zone, reduces the number of applications you need open, and makes the common tasks fast enough that you stop thinking about them.

What Does Terminal-First Actually Mean?

A terminal-first workflow is not about being a purist or refusing to use graphical tools. It is about defaulting to the shell for tasks where the shell is genuinely faster, and reaching for graphical tools only when they provide clear value over the command line alternative. Reading logs, searching code, navigating the filesystem, managing Git, running tests, and interacting with APIs are all things the shell does exceptionally well. Writing prose, reviewing complex diffs, and designing UI are places where graphical tools earn their keep.

The goal is not ideology. The goal is reducing the surface area of your daily work so that you spend less time managing windows and more time doing the work itself.

Starting with the Right Shell

If you are on macOS, the default is zsh. On most Linux distributions, it is bash. Both are fine. If you want a modern shell with better autocomplete, spell correction, and scripting capabilities, fish is worth a look. It works out of the box without the configuration rabbit hole that zsh users know well.

The shell choice matters less than you might think. What matters is that you learn it well enough to customize your prompt, set up aliases for commands you type repeatedly, and write small functions for multi-step workflows you find yourself performing daily.

A Useful Prompt

Your prompt is the single piece of UI you see more than any other. If it shows you the current directory, the Git branch, and whether the working tree is dirty, you save yourself thousands of keystrokes over the course of a week. Tools like Starship make this trivial to set up and work across every shell.

# Install Starship
curl -sS https://starship.rs/install.sh | sh

# Add to your shell config
eval "$(starship init zsh)"

Starship shows your language version, Git status, Kubernetes context, and AWS profile by default. It is fast because it is written in Rust, and it is configurable enough that you can strip away anything you do not use.

The Multiplexer: tmux or zellij

A terminal multiplexer lets you split your screen into panes, create multiple window sessions, and detach from processes so they keep running after you close the terminal. If you have ever SSHed into a server, started a long build, and then accidentally closed the tab, you already understand the value.

tmux is the established choice. Its keybindings take a day to learn and a week to love. zellij is a newer alternative with a more intuitive default layout and built-in tab management. Either one gives you the ability to run your editor, a test watcher, and a log tail in side-by-side panes without touching your mouse.

# tmux basics
tmux new -s work     # create named session
Ctrl-b %             # split vertically
Ctrl-b "             # split horizontally
Ctrl-b d             # detach (processes keep running)
tmux attach -t work  # reattach

The productivity gain from a multiplexer is not subtle. You stop opening new terminal windows and tabbing between them. Everything lives in one workspace that you can arrange once and reuse.

Faster File Navigation with fzf

fzf is a fuzzy finder for the command line. It is one of those tools that sounds simple until you use it, and then you cannot imagine working without it. It integrates with your shell so that Ctrl-r (reverse history search) becomes interactive, and Ctrl-t lets you fuzzy-select files from the current directory and pipe them into any command.

Combined with ripgrep (rg) for searching file contents, you can find anything in a codebase in under a second. No loading a IDE project index, no waiting for the search bar to populate, no clicking through a tree view.

# Search for a function across the repo
rg "def handle" --type py

# Interactively find a file and open it
vim $(fzf)

# Use fzf to filter ripgrep results
rg --files | fzf --preview "bat --color=always {}"

Git Without the GUI

Git is a terminal tool. The graphical clients are fine for beginners, but once you understand the command-line interface, it is faster and more capable than any GUI. The key is learning a handful of commands well and then building aliases for the sequences you type over and over.

# Useful Git aliases
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.st "status -sb"
git config --global alias.lg "log --oneline --graph --decorate --all"
git config --global alias.aliases "config --get-regexp ^alias"

With git lg, you get a visual commit graph that rivals anything in a GUI client, rendered directly in your terminal. With git st, you get a concise status line showing branch and tracking info. These are small things that add up to minutes saved per day.

Watching Tests While You Code

One of the biggest advantages of a terminal-first setup is the ability to run a test watcher in a split pane alongside your editor. Every time you save a file, the relevant tests re-run automatically. You see pass or fail in your peripheral vision without breaking flow.

# JavaScript
npx vitest --watch

# Python with pytest-watch
ptw -- src/tests/

# Go
gotestsum --watch ./...

This is the tightest feedback loop you can build. Save, see results, adjust. No alt-tabbing to a browser, no waiting for a CI pipeline to pick up your push. The latency between writing code and knowing whether it works drops from minutes to seconds.

API Calls Without Leaving the Shell

For quick API exploration, curl plus jq is often faster than opening Postman or Insomnia. You can pipe JSON responses through jq to extract exactly the field you need, and you can save common requests as shell functions.

# Get a formatted JSON response
curl -s https://api.github.com/repos/cli/cli | jq '.stargazers_count'

# Save a reusable function
gh-stars() {
  curl -s "https://api.github.com/repos/$1" | jq '.stargazers_count'
}
# Usage: gh-stars cli/cli

Choosing the Right Terminal Emulator

Not all terminal emulators are equal. If you are on macOS, the default Terminal.app is fine but slow compared to alternatives. iTerm2 remains the standard for power users on macOS, with split panes, profiles, triggers, and deep customization. On Linux, GNOME Terminal and Konsole are both solid, while Alacritty and WezTerm offer GPU-accelerated rendering for users who want maximum performance and live in tmux for window management.

WezTerm deserves a special mention because it is written in Rust, supports ligatures, and has a Lua-based configuration that lets you script window layouts, tab naming, and even dynamic theming based on time of day. It also has built-in multiplexer features, though most users still pair it with tmux for the portability of session management across machines.

Dotfiles: Your Setup as Code

The final piece of a terminal-first workflow is managing your configuration as code. Your dotfiles, the collection of shell configs, aliases, functions, and tool settings, should live in a Git repository. This way, when you set up a new machine, you clone the repo, run a script, and your entire environment is back in minutes.

# Typical dotfiles structure
~/dotfiles/
  zsh/.zshrc
  git/.gitconfig
  tmux/.tmux.conf
  nvim/init.lua
  starship.toml
  install.sh

There are frameworks like stow and chezmoi that automate the symlinking process, or you can write a simple install script. The point is that your environment becomes reproducible. When you get a new laptop or spin up a cloud dev environment, you are productive within the first ten minutes rather than the first day.

When to Leave the Terminal

Terminal-first does not mean terminal-only. There are tasks where graphical tools are genuinely better. Reviewing a large pull request with a side-by-side diff is easier in a browser or IDE. Designing a database schema benefits from a visual ERD tool. Debugging a complex CSS layout is faster with browser DevTools. The point is to be deliberate about when you switch contexts, rather than defaulting to the graphical tool out of habit.

A good rule of thumb: if you are doing something you could describe in a single sentence, the terminal can probably do it faster. If you need to see and manipulate multiple complex objects simultaneously, reach for a graphical tool.

The Compounding Effect

Here is the thing about a terminal-first workflow: the benefits compound. Every alias you write, every function you define, every pane layout you save, shaves a few seconds off a task you perform dozens of times per day. Over a week, that is hours. Over a year, it is days.

More importantly, the cognitive overhead drops. You are not managing six applications. You are not hunting for the right tab. You are not waiting for a GUI to load. You are in one environment, speaking one language, and the computer is responding at the speed of your typing.

That is what terminal-first means. Not purity, not aesthetics, not showing off. Just less friction between thinking and doing. The terminal is the shortest path from an idea to its execution. Set it up right, learn it well, and it pays you back every single day.
