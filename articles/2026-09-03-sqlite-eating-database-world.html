SQLite Is Eating the Database World (Again)

Opened Terminal | September 3, 2026

Every few years, someone rediscovers SQLite and writes a blog post about how it is the most widely deployed database in the world. That claim was true in 2012 and it is still true today, with over one trillion active deployments across mobile devices, embedded systems, desktop applications, and web browsers. But the story in 2026 is not about the past. It is about what is happening right now: SQLite is quietly becoming the default database for AI workloads, edge computing, and local-first software. The database you dismissed as a toy is eating the stack from the bottom up, and the reasons are not nostalgia. They are structural.

If you are building a new application in 2026 and you are not at least evaluating SQLite as your primary database, you are probably over-provisioning. Here is what changed.

The Postgres Default Is a Tax You Stopped Noticing

For the last decade, Postgres has been the default database for new applications. It is the right choice for a wide range of workloads. It is reliable, extensible, and battle-tested at scale. But it carries a cost that most teams stopped calculating because everyone pays it.

That cost is infrastructure. Postgres requires a server. That server needs provisioning, networking, backups, monitoring, and a failover strategy. In a cloud environment, that means a managed instance with a monthly floor cost. On edge platforms, it means connection pooling through PgBouncer or a serverless proxy. Every layer adds latency, cost, and operational complexity.

For most applications, the traffic profile does not justify this. The median web application handles a few hundred concurrent users, writes less than a few thousand rows per minute, and needs data locality more than horizontal scale. SQLite is the right tool for the median.

SQLite runs in-process. No server. No network calls. No connection pool. No authentication layer. The database is a file on disk, and the library that reads and writes it lives in your application's memory space. The latency of a query is the latency of a function call, not a network round trip. For a local-first application, that is the difference between instant and sluggish.

WAL Mode Changed the Conversation

The technical objection to SQLite has always been concurrency. In the default journal mode, SQLite locks the entire database file during writes. That means one writer blocks all readers. For a web application with concurrent requests, that is a dealbreaker.

Write-Ahead Logging (WAL mode) changed this. In WAL mode, writes go to a separate log file before being merged into the main database. Readers access the main database file without blocking. Writers append to the log. Concurrent reads and writes coexist without contention, up to the point where a checkpoint merges the log into the main file. For most workloads, that checkpoint happens fast enough that the contention never surfaces.

WAL mode has been available since 2010, but it took the ecosystem years to treat it as the default. In 2026, most SQLite drivers enable WAL mode automatically or recommend it in their getting started guides. SQLite now handles concurrent read and write workloads that would have required a server-based database ten years ago.

The remaining limitation is multi-process writes. WAL mode allows concurrent reads from multiple processes, but only one process can write at a time. For a single-server application, that is fine. For a distributed deployment, it is not. This is where the modern SQLite ecosystem has filled the gap.

LiteFS and the Distributed SQLite Stack

Fly.io built LiteFS to solve the one problem SQLite could not solve on its own: running the same database file across multiple machines. LiteFS is a distributed filesystem that replicates SQLite database files across nodes. One node is the primary, which handles writes. Other nodes are read replicas that serve local copies of the database file. Writes are forwarded to the primary and replicated to replicas through a log.

This gives you the best of both worlds. Reads are local function calls with zero network latency. Writes go through a single primary but replicate to all nodes. The failover story is not as seamless as a managed Postgres cluster, but it is good enough. And the cost is a fraction of what you pay for a managed database with the same throughput.

Cloudflare launched Durable Objects SQLite, which runs SQLite inside their edge workers. Turso built a distributed SQLite hosting platform on top of libSQL, an open-source fork of SQLite with vector search and replication built in. Turso handles production traffic for thousands of applications. Cloudflare's edge database is the backbone of features that millions of users interact with daily.

Vector Search Without a Vector Database

The AI boom created a wave of specialized vector databases. Pinecone, Weaviate, Qdrant, and Milvus all raised money and shipped products for storing embeddings and running similarity searches. But for most AI applications, the vector count is in the thousands or tens of thousands, not billions. At that scale, a dedicated vector database is overkill.

SQLite now supports vector search through extensions like sqlite-vec, which implements vector similarity operations natively inside SQLite. You store embeddings in a regular table, create a virtual table with a vector index, and run similarity searches with standard SQL. No separate service, no API call, no network latency between your application and the vector store. The embedding and the row it belongs to live in the same database file.

For RAG applications, this is the difference between a simple architecture and a distributed one. Your chunk text, your embeddings, your metadata, and your conversation history all live in one SQLite file. You query it with SQL. You back it up by copying a file. You deploy it by shipping the file. The simplicity is not a compromise. It is the point.

For the workloads that need a dedicated vector database, billions of vectors with real-time updates across a cluster, those products exist and they work well. But the number of applications that need that scale is small. The number that could ship faster and cheaper with sqlite-vec is large and growing.

Local-First Is Not a Niche

The local-first software movement is a response to a real problem: applications that depend on a remote database for every operation feel slow, break when the network fails, and create a dependency chain that makes every feature harder to build. Local-first applications store data locally, sync when the network is available, and work offline by default.

SQLite is the foundation of this pattern. CR-SQLite enables conflict-free replicated data types (CRDTs) on top of SQLite, allowing multiple peers to write to their local copies and merge changes without conflicts. ElectricSQL provides bidirectional sync between a local SQLite database and a remote Postgres instance. The application reads and writes locally. The sync layer handles the distributed state.

The result is applications that are fast by default and resilient by design. The latency of reading from a local SQLite file is under a millisecond. The latency of reading from a remote database over the network is 50 to 200 milliseconds, even with connection pooling. Users notice the difference. They do not know why one app feels instant and the other feels sluggish, but the database choice is the reason.

When to Use What

SQLite is not a universal replacement for Postgres. There are workloads where Postgres is the right choice and SQLite is the wrong one. High-write-throughput applications with dozens of concurrent writers hitting the same table will hit SQLite's single-writer bottleneck. Applications that need materialized views, complex full-text search ranking, or native partitioning will find Postgres more capable.

The decision comes down to a simple question: do you need a server-based database, or do you need a database? Most applications need a database. They need persistence, queries, transactions, and reliability. SQLite provides all of those in a 600-kilobyte library with no operational overhead.

The teams that have already made the switch report the same things: lower costs, faster development, simpler deployment, and fewer incidents. Not because SQLite is more powerful than Postgres. Because it is simpler. The complexity you remove is the complexity you do not debug at three in the morning.

SQLite has been eating the database world for twenty years. It is doing it again, and this time the application stack is catching up. The tools, the runtimes, and the deployment platforms are converging on a model where the database is a file, not a service. If you have not looked at SQLite since you used it for prototyping, look again. The database you dismissed is the database your competitors are shipping with.
