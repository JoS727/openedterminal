The AI Gateway Pattern: Why Every Platform Team Is Building One

Opened Terminal | August 20, 2026

Every platform team that has shipped a production AI feature has arrived at the same architectural conclusion, usually after a costly incident. You do not call an LLM provider directly from your application. You build a layer between your application and the model, and that layer handles routing, cost, observability, fallback, and policy. The industry has converged on a name for this layer: the AI gateway.

If your team has not built one yet, you will. If you have built one, you are probably rebuilding it. Here is what the pattern looks like, why it emerged, and what it does that your provider's SDK does not.

The Problem With Calling Models Directly

The simplest AI integration is a direct API call. Your application imports the OpenAI or Anthropic SDK, constructs a prompt, sends a request, and receives a response. This works for a prototype. It works for a weekend hack. It does not work in production, and the reasons are not about scale. They are about failure modes.

Model providers rate limit. They throttle tokens per minute, requests per minute, and concurrent requests. When you hit a limit, you get a 429 with a retry-after header and no guidance on what to do next. Your application either retries blindly, waits too long, or crashes the request that a user is staring at. In production, that means a support ticket.

Model providers also go down. In 2026, the major providers have multi-region outages several times per quarter. When your only integration is a direct call to one provider, an outage takes your feature offline. Your on-call engineer gets paged, opens a dashboard, and sees that someone else's infrastructure is the problem. There is nothing to fix. You wait.

The third failure mode is cost. LLM pricing is token-based, and token counts are unpredictable. A single user who sends a large document through your summarization endpoint can spend more in one request than the rest of your users spend all day. Without a gateway, you find out about this when the monthly bill arrives.

What the Gateway Does

An AI gateway is a service that sits between your application and one or more LLM providers. Your application calls the gateway's API, which has the same shape as a provider's API. The gateway forwards the request to the provider, collects the response, and returns it to the application. That is the baseline. The value is in everything else the gateway does between receiving the request and forwarding it.

Routing. The gateway decides which model handles each request. A summarization endpoint might route to a small, fast model. A coding assistant routes to a larger model with better reasoning. A classification task routes to the cheapest model that meets your accuracy bar. Routing can be static, based on endpoint, or dynamic, based on request length, user tier, or feature flags. The point is that the decision lives in one place, not scattered across your codebase.

Fallback. When a provider returns a 429 or a 500, the gateway retries against the same provider with exponential backoff. If retries fail, it falls back to a second provider. If you are calling OpenAI and it throttles you, the gateway forwards the same request to Anthropic or a self-hosted model. The application does not know the fallback happened. The user does not know. The gateway handles it in milliseconds and logs the event.

Cost control. The gateway counts tokens before and after each request. It enforces per-user, per-endpoint, and per-tenant budgets. When a user exceeds their daily token allowance, the gateway returns a 402 or a rate limit response instead of forwarding the request to the provider. You set the limits in configuration, not in code. The cost surprises stop because the gateway makes them impossible.

Observability. The gateway logs every request: the prompt, the response, the model, the token count, the latency, the cost, and the status. It exposes metrics through Prometheus or OpenTelemetry. You see dashboards for token spend, error rate, p95 latency, and model distribution. When a user reports that an AI feature is slow or wrong, you have the request trace. Without a gateway, you are guessing.

Build or Buy

The gateway pattern has matured enough that you have both build and buy options. The open source projects worth knowing about are LiteLLM, which provides a unified API across providers with routing, fallback, and cost tracking, and Portkey, which adds caching and observability. Cloudflare launched AI Gateway as a managed service that handles routing, caching, and rate limiting at the edge. Vercel built AI SDK with a similar abstraction layer for frontend and edge deployments.

For most teams, the buy decision is correct for the first iteration. LiteLLM handles the hard parts: provider compatibility, token counting, retry logic, and fallback chains. You deploy it as a container or a serverless function, configure your provider keys, point your application at it, and you have a gateway in an afternoon.

The build decision becomes correct when your needs diverge from what the open source tools provide. If you need custom routing logic based on user history, fine-grained tenant isolation, or integration with your internal observability stack, building a thin gateway on top of your existing service framework is straightforward. The core is a reverse proxy with middleware. The hard parts are the provider SDKs and the token counting, which you can extract from LiteLLM or implement directly.

Most teams end up in the same place: start with LiteLLM, hit its limitations, and build a custom gateway that reuses its provider abstractions. That is a reasonable path. The wrong path is calling providers directly from your application and building ad hoc retry logic in every service that uses AI.

Policy and Safety Belong in the Gateway

The gateway is also the right place to enforce policy. If your product has content moderation requirements, prompt injection detection, or PII redaction, those checks belong between the user and the model, not after the model responds. The gateway can inspect every prompt before it reaches the provider, reject requests that violate policy, and log violations for review.

This matters because policy enforcement in the application layer is fragile. Each new endpoint that calls an LLM needs to implement the same checks. A developer forgets one, and you have a policy gap. The gateway centralizes enforcement. Every request goes through the same pipeline regardless of which service initiated it.

Caching is the other feature that belongs in the gateway. LLM responses are deterministic for a given model and prompt temperature, and many workloads have repeated prompts. A cache hit costs nothing and responds in milliseconds. LiteLLM and Portkey both support response caching keyed on prompt hash and model. For high-traffic endpoints with repeated prompts, caching cuts your token spend by a significant margin with zero configuration on the application side.

The Cost Question

Teams building their first AI feature almost always underestimate cost. The gateway forces visibility. When you see token spend per endpoint, per user, and per model in a dashboard, you start making different decisions. You route more traffic to smaller models. You cache more aggressively. You set per-user limits that prevent a single power user from burning your margin.

The teams that shipped AI features in 2024 and 2025 without a gateway are the teams that got surprise bills. The teams shipping in 2026 are building the gateway first, before the first production request.

What Changes When You Have One

The first thing that changes is incident response. When a provider goes down, your on-call engineer sees the fallback fire in the gateway dashboard. The feature stays online. The incident is a note in the postmortem, not a page that wakes someone at three in the morning.

The second thing that changes is velocity. New AI features become a new route in the gateway configuration, not a new SDK integration with its own retry logic and error handling. A developer adds an endpoint, sets a model and a cost limit, and ships. The gateway handles the rest.

The third thing that changes is cost predictability. You see token spend in real time. You set budgets that enforce themselves. The monthly bill is not a surprise. It is a number you already saw in a dashboard and already adjusted for.

The AI gateway is not a luxury. It is the minimum viable infrastructure for running AI in production. Every platform team that has shipped AI to real users has built one or wishes they had built it sooner. If you are calling a model provider directly from your application right now, your first production incident is a provider outage you cannot control. Build the gateway first.
