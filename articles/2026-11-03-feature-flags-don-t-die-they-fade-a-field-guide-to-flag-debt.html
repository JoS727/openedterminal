Feature Flags Don't Die, They Fade: A Field Guide to Flag Debt

openedterminal.com  |  November 3, 2026  |  Tech / News

Every mature codebase has a ritual nobody scheduled: someone runs the internal flag dashboard, sorts by age, and discovers a flag called checkout-v3-optimized-pricing-engine that was created twenty-two months ago, defaults to the new behavior, and is now genuinely load-bearing in a way its author never intended. The cleanup ticket has been open since the author left for another company. Nobody deletes it because nobody knows for certain what it does anymore, and the one person who could say so is gone. That flag is not a feature toggle. It is sediment.

The reason flags accumulate is structural, not personal. Decoupling deploy from release is genuinely one of the best practices of the last decade — trunk-based development, dark launches, instant kill switches for the pricing page at 2 a.m. — and each of those wins is real. The cost side of the ledger, though, is paid on a different schedule by different people, which is why nobody counts it at purchase time. Every flag in a system multiplies its testable states. Ten flags is a thousand code paths; three flags interacting in a payment flow is a combinatorics problem that your integration suite only samples. Flags also harden over time: a flag that gates a migration becomes the only place the old tables are written to, and suddenly removing it is a database project, not a config change. The migration tool you built to make the flag removeable got archived; the flag did not.

The fix is not discipline — "remember to delete your flags" ranks with "remember to floss" as an organizational strategy. The fix is making flag debt visible and expensive at the point of creation, the same way linting made style arguments unnecessary. Concretely: every new flag ships with metadata at creation time — owner as a team, not an individual; a creation date; a declared expiry; and a category, because a kill switch and an A/B test and a long-term entitlement have completely different legitimate lifespans. A kill switch for the checkout flow may justifiably live for years. An A/B test that is still on after six weeks is not an experiment; it is a decision your company has been making by default.

Then wire the registry into CI instead of into culture. A check that fails the release when a flag is past its declared expiry converts "we should really clean up" from an appeal into a gate, and gates work while appeals do not. Better still, make the expiry removal a first-class change: many teams have had success with automated removals — flag defaults flipped to the winning branch, dead branches deleted, referenced code stripped — reviewed like any other PR, precisely because a human doing it by hand will always prioritize something newer and shinier. The teams that keep their flag counts flat do not have more virtuous engineers. They have a system where the default path, the lazy path, and the correct path are the same path.

Two operational details separate serious flag hygiene from a dashboard nobody opens. First, two-sided flags — flags whose value differs across a shard, a tenant, or a region — are where incidents hide, so flag state belongs in observability: any debugging session over a misbehaving request should be able to print the flag values that request was evaluated against, or you will spend your next incident bisecting behavior that turned out to be a percentage rollout. Second, beware the flag that hides a schema change. The one-way door matters: a flag that gates reads is revertible; a flag that gates writes against a migrated schema is not, because rolling it back means the old code meets the new tables. Those deserve an explicit naming convention and a senior sign-off, precisely because they cannot be treated as reversible later.

None of this is glamorous, which is the point. Flag debt, like dependency debt, is a slow tax with no single dramatic outage — it shows up as slower onboarding, test suites that get skipped "temporarily," and incidents with two root causes where one is a flag combination nobody imagined. A quarterly deletion pass that removes the bottom decile of your registry, an expiry gate in CI, and a rule that flags get owners on day one will keep the system legible. The alternative is a checkout that works for reasons buried under two years of sediment, and the engineer who understands the checkout-v3-optimized-pricing-engine flag is not available, because the checkout it stabilized was replaced in the spring.
