Your CI Is Not Slow Because of Your Tests

openedterminal.com  |  November 1, 2026  |  Tech / News

Your test suite is not slow. Your tests run in ninety seconds. Your pipeline takes nineteen minutes to run those same ninety seconds of tests, and the difference — the other eighteen and a half minutes — is a distributed systems problem that you have been treating as a fact of life. It is time to stop paying it.

Start with the checkout tax. Every pipeline run clones the repository, and most organizations have quietly let their repos grow to two or three gigabytes of history, LFS assets, and vendored binaries. A cold clone on a busy shared runner is minutes, not seconds. Shallow clones with fetch-depth: 1 cut this drastically, but the real fix is architectural: if a submodule bump requires fetching a decade of history, your repo layout is making tax payments to Git for services you never ordered.

The second tax is artifact churn. The median CI setup rebuilds the world on every run: base images, dependency wheels, compiled language bindings, the same frontend bundle rebuilt from identical source. A well-configured cache keyed on the lockfile hash turns this into a no-op; a badly keyed one silently misses every time and you never notice, because green means green. Audit this once — print the cache hit ratio, look at it — and you will typically find it hovering near zero for reasons nobody can reconstruct.

Third is the flaky-test surcharge, and this one compounds. A test that fails one run in twenty converts every hundred runs into five reruns, five investigations, five moments where a tired engineer stares at a diff looking for a crime that was never committed. Worse, the team's response — an automatic retry — teaches the pipeline to hide its own disease. Each retry masks the signal that made the flake visible. Eventually you have a suite where real failures hide inside tolerated noise, and nobody can say when the rot started. The fix is unfashionable: quarantine the flake the same day, fix it within a week, and log the retry rate as a first-class metric next to pass rate.

Then there is parallelism, which most teams believe they have and do not. Splitting four thousand tests across eight shards is not parallelism if shard one inherits an initialization step that takes four minutes while the others idle. Rebalance by measured duration, not by file count, and watch wall-clock time drop by half with zero code changes. The tooling for this exists in every major CI platform; what is missing is the measurement, because duration data lives in the CI provider's dashboard and dies there instead of feeding back into the split.

None of this requires new infrastructure or budget approval. It requires treating pipeline time the way you treat p99 latency: as an SLO with an owner. Put the number on a dashboard. When it regresses, page someone. The teams with the fastest feedback loops are not the ones with the best hardware — they are the ones who noticed, some months ago, that nineteen minutes was a decision someone made quietly, and decided to un-make it.
